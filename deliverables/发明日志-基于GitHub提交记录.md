## 二、发明目标与核心问题

我们的目标不是制作一个只能远程开关水泵的花盆，而是制作一个面向太空育种研究的地面原理样机，使植物在网络或上位机失效时仍能维持基本生长，同时利用云端模型加快环境诊断和早期表型筛选。

研发过程中聚焦五个核心问题：

1. **生存安全**：断网、云端模型失败或树莓派离线时，植物不能失去基本浇水和补光能力。
2. **硬件资源约束**：ESP32 同时承担 Wi-Fi、OLED、串口、传感器和执行器时存在内存不足和实时性下降。
3. **AI 权限边界**：大模型可以提出建议，但不能绕过温度、时长、频率等本地安全护栏。
4. **单舱育种比较**：只有一个种植舱时，需要通过固定 ROI、舱内对照组与候选组、跨周期重复记录形成可比较证据。
5. **可展示、可追溯**：传感器、执行器、AI 判断、照片、人工复核和实验日期应在网页端形成清晰的证据链。

### 记录 08｜2026-05-28：提出 Decision Plane / Action Plane 分离

**发现的问题**

传感器或 AI 可以发现缺水、缺光、温度异常、缺素风险等多维问题，但实物只有水泵和补光灯。如果把“发现问题”和“必须执行动作”等同，会导致虚假执行器或不安全动作。

**发明性设计**

- 将系统分成**决策层**和**执行层**：决策层可以广播多种诊断信号，执行层只执行真实硬件支持且通过护栏的动作。
- 建立 12 类状态信号、物理/建议型信号分类和 WS2812 动画映射。
- AI 输出增加 `signals` 和 `breeding_observation`，服务端对枚举和文本长度进行校验。
- 新增 COB 补光灯执行器，并让大屏展示“输入—判断—输出”的决策链。

**验证与证据**

- 自动化测试由 87 项增加到 101 项。
- 代表提交：`d614606`；相关硬件提交：`71df7ce`。

### 记录 09｜2026-05-28—05-29：解决 Wi-Fi OOM、按键迟钝和菜单黑屏

**实机现象**

- ESP32 Wi-Fi 初始化偶发内存不足。
- 主循环每秒才检查一次按键，操作延迟明显。
- 菜单重新初始化显示模块后仍持有旧引用，导致黑屏。

**根因与修正**

- 将重模块改为懒加载，并把 Wi-Fi 初始化提前，可用内存由约 129 KB 提高到约 149 KB。
- 将按键轮询从约 1 Hz 提高到约 10 Hz，修正 ADC 阈值并增加均值采样。
- 取消错误的显示释放/重建顺序，统一红黄导航、绿键确认、蓝键返回。
- 重新设计 OLED 三页界面和手动操作反馈。

**结果与证据**

- 形成一次有明确“现象—根因—修复—复测”的工程闭环。
- 代表提交：`39f918a`、`55c364e`。

### 记录 10｜2026-05-30：升级为 ESP32 + 树莓派双层架构

**实机问题**

ESP32 同时启用 Wi-Fi、UART2、OLED/I²C 和较多业务模块时出现内存压力，甚至发生 UART 初始化失败或重启。继续让 ESP32 直接联网和调用云端模型不利于稳定运行。

**架构决策**

- ESP32 作为舱内飞控：负责传感器、本地规则、安全护栏和执行器。
- 树莓派作为载荷计算机：负责联网、云端 AI、遥测转发和后续视觉处理。
- 两者使用 UART2、115200、JSON-over-Line 交换 `report/ping/pong/advice`。
- 将 DeepSeek 调用从 ESP32 迁移到树莓派 `pi_advisor`。
- 删除 ESP32 直接 Wi-Fi、AI 和遥测的旧路径，使双层架构成为唯一正式路径。

**验证与证据**

- 完成串口双向通信、树莓派 systemd 自启动和云端状态转发。
- 发现并修复共地松动、串口控制台争用和硬件看门狗误杀等实机问题。
- 阶段测试记录为 144 项，重构删除旧路径后为 133 项。
- 代表提交：`5abc578`、`2542a16`、`1e34151`、`2901636`。

### 记录 11｜2026-05-31：完成真机闭环并把降级链简化为两层

**验证目标**

验证“ESP32 → 树莓派 → 云端模型 → 树莓派 → ESP32 → 执行器/大屏”的完整链路，同时避免重复决策层。

**实施结果**

- ESP32 报告经 UART 到达树莓派，树莓派调用模型生成建议并返回。

- 删除树莓派固定阈值中间层，将降级链由三层简化为：①云端模型；②ESP32 本地规则。
- 统一种植天数从 D1 起算，避免 OLED 与网页日期不一致。

**结果与证据**

- 形成“联网时增强、断联时自治”的正式架构。

## 四、形成的主要技术创新点

### 1. 面向断联环境的双层自治架构

ESP32 保留维持植物生存所需的感知、规则、安全护栏和执行能力；树莓派承担联网、云模型、视觉和云端同步。上位机失效只会降低智能程度，不会直接让基本养育停止。

### 2. 决策能力与执行能力分离

系统可以识别多种风险和育种观察，但只对已经安装的水泵、补光灯下发动作，并且动作必须经过本地温度、时长和频率限制。这解决了“AI 能说很多，但硬件不能盲目执行”的问题。

### 3. 环境控制与表型筛选两条 AI 链路隔离

传感器链负责水泵和补光决策；照片链负责育种选型。多模态模型发现叶色或株型异常时只生成筛选证据，不直接驱动执行器，降低视觉误判伤害植物的风险。

### 4. 单装置条件下的舱内对照与纵向重复

同一相机画面划分固定 ROI，在相同光照、温湿度和拍摄参数下同时记录对照组和候选组；再通过多个独立种植周期计算相对对照差异、中位数和离散程度。该方案不声称等同于多舱科研试验，但能在单装置条件下形成可解释的早期筛选证据。

### 5. 可追溯视觉证据链

从拍摄条件、质量门、原图、AI 分析、人工标签到云端同步均保留事件编号和时间信息；实验天数由播种日期和系统时间自动计算，并允许人工修正和记录操作者。

## 六、当前完成度与仍需继续记录的实验

### 已形成工程闭环

- ESP32 传感器、本地安全规则、水泵、补光灯、OLED、按键和 WS2812 状态显示。
- ESP32 与树莓派 UART 双向通信、树莓派 AI 建议和云端实时大屏。
- Camera Module 3 定时拍摄、质量检查、多模态 API 分析、SQLite 事件记录和云端同步。
- 实验日期初始化、手动日龄修正、人工复核接口和网页双主题显示。
- 当前代码自动化测试：201 项通过。

### 仍需通过真实实验补齐

1. 固定四个种植 ROI 的边界、编号和实物标记。
2. 明确对照组种子来源、候选组处理差异、每组株数和随机化方式。
3. 至少完成多个独立种植周期，记录发芽率、叶面积趋势、株高、叶色、异常和淘汰理由。
4. 用人工测量结果抽查多模态模型结论，统计一致与不一致案例。
5. 记录每次相机高度、角度、补光条件和舱内维护操作，避免把拍摄变化误认为生长变化。
6. 对泵、灯、断网、断 Pi、模型超时、磁盘不足和云端不可达进行持续故障演练并签字留档。
